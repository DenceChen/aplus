# 变异台自身的变异规格（第 121 层）

## 为什么台子自己也要被变异验证

仓里每一个 `✅ S<n> 被杀` 都建立在**变异台把变异正确执行、正确计分**之上。
今天实测它坏过两次，两次都**自己发了信用**：

| 变异 | 台子给什么 | 实际 |
|---|---|---|
| `if False:` 顶格（语法炸弹） | `rc=2` ⇒ ✅「守住了」 | 被测文件压根解析不了，**守卫一条都没跑** |
| `return 1` → `return 2`（**同长度**） | 报**存活**（保守） | 旧 `.pyc` 被命中 ⇒ **变异对被测模块等于没发生** |

第二条的失效方向值得单说：它**不会**给假信用，会报「存活」——
而「存活」会被读成「**守卫有洞**」，于是人去改一条本来正确的守卫。
**那是本仓最贵的错误方向**（失败方向判断错比算错严重一个数量级）。

## 三条 spec 各钉住台子的哪一道关

| Spec | 摘掉的是 | 被谁杀掉 |
|---|---|---|
| H1 | `compile(mutant)` 前置检查 | `test_a_mutant_that_cannot_even_be_parsed_…`（它断言「跑 pytest 之前就被挡下」） |
| H2 | `drop_bytecode_cache(p)` | `test_a_mutant_that_really_breaks_…`（同长度变异）+ `test_the_bytecode_cache_of_the_mutated_file_is_actually_dropped` |
| H3 | `elif rc == 1:` 退回 `elif rc != 0:` | `test_a_valid_mutant_that_breaks_collection_is_still_not_credited` |

## 两条纪律（形状 14 的三个入口，同一个洞）

变异台只问「变异后红了吗」，从不问：
① 变异前绿吗（正控臂）；
② 变异体**是不是合法 Python**；
③ 变异体对**被测解释器**是不是真的变了。

第 14 层那次是「压根没写进去」，第 121 层这两次是
「写进去了但没被看见」和「写的是垃圾」——
**三种形态的输出长得一模一样**，所以必须每种各有一条 spec。
