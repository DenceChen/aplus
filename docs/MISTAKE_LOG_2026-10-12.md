## 36. 把退市股误判成「文件被截断」，差点去修一个不存在的 bug

**经过**：昨天判定「591 只行数偏短 = 501 只次新股 + **90 只可疑截断**」，
并写下「结构上不可能截断，必有代码绕过 store 直接 `to_parquet`」。

**实际**：`coverage.py` 的 docstring 里早就写着这件事需要上市/退市登记才能判，
而我用行数阈值重造了一遍更差的启发式。今天用 baostock 登记簿全量复核：

    行数 < 1882 的 2122 只 = 236 退市 + 1886 次新股 + **0 无法解释**

`000418.SZ` 退市日 2019-06-21，文件末行正好 2019-06-21。

**更该早发现的旁证**：截断股的 mtime 散布在 10-09 23 / 10-10 08 / 10-10 21 /
10-11 15 四个时段，与正常股无异。**mtime 分散就说明不是某一次坏写入**——
这条反证当时就在手边，我没有用它推翻自己的假设。

**教训**：提出「必有代码绕过了存储层」这种**结构性断言**之前，
先排除平凡解释（新股、退市、停牌）。以及：项目里已有的权威判据
（登记簿）要用，不要因为「更快」而用更差的启发式。

**代价**：如果没查就动手，我会写坏 236 只**已经正确**的退市股历史——
用远端数据覆盖掉本来就对的东西。

## 37. 同一个「尾部缺失根数」连写两版 numpy 一行式，两版都错

**经过**：为了统计 `turn` 列末尾连续缺失多少根，我先写：

```python
d = int((~t.notna().to_numpy()[::-1]).argmax())      # 第 1 版：错
```

`argmax` 找的是「从末尾往前第一个 NaN 的下标」，不是「末尾连续 NaN 的个数」。
结果：`300302.SZ` 明明末根 `turn=4.2583` 有值，却被判成「缺 1871 根」。

改成：

```python
d = int((~v)[::-1].argmax())                          # 第 2 版：还是错
```

末根**有效**时，`reversed[0]` 是 False，`argmax` 会跳过它去后面找 NaN，
于是报出一个荒谬的深度。

两次都靠**随手打印真实数据**才发现：

    300302.SZ 脚本算缺 1871 根；实际末根 turn=np.float64(4.2583)

**教训**：连着两次在同一处翻车，说明该换的不是写法而是策略。
第三次我改成一秒钟能看懂、几乎不可能写错的笨办法：

```python
for x in reversed(vals):
    if is_nan(x): d += 1
    else: break
```

**「聪明」的一行式在我这里的期望产出是负的。**
涉及计数、边界、NaN 语义的代码，宁可写成啰嗦的循环。

## 38. 自己写的「宁可吵，不可静默」原则，自己没遵守

**经过**：给 `tail_nan_columns()` 写停牌排除时，我同时查了
`volume > 0` 和 `tradestatus != 0`，并在注释里写：

> `tradestatus=0` 而 `volume>0` 属数据自相矛盾——按成交处理。宁可吵，不可静默。

红测试也确实抓到了（`test_tradestatus_zero_with_positive_volume_still_counted` 红了），
但我的第一反应是去改**测试**。看了报错才意识到是**实现**违背了自己的注释。

**最终**：删掉 `tradestatus` 这一支，只用 `volume > 0`。

**教训**：
1. 注释里写了原则，实现就要符合；不符合就是实现错了，不是测试错了。
2. 多一个条件分支，就多一个「把错误变成别的形状」的机会——
   两个条件冲突时，删掉信息量更少的那一个，比加特判更稳。

## 39. 变异体「存活」：测试写了，但钩子没接上

**经过**：给写库锁加了两个变异体（删掉 `_held` 护栏、去掉 pid 归属核对），
跑出来 2/4 存活。我判断是「测试弱」，于是补了两个新测试
（`test_release_does_not_steal_same_process_lock`、
`test_release_does_not_steal_replaced_lock`），新测试全绿——**变异体照样存活**。

真实原因：变异体清单里写的目标测试还是
`["tests/test_write_lock.py::test_release_is_idempotent"]`，
**我新写的两个测试根本没挂进去**。

**教训**：写了测试 ≠ 测试在起作用。
新增防护测试后要立刻确认它**出现在对应变异体的目标清单里**——
否则「变异体存活」和「测试无用」这两条结论都是假信号，
而且它们指向的修复方向完全相反（一个是补测试，一个是改实现）。

## 40. 测试帧的起点和体检窗口对不上，测的变成另一个缺口

**经过**：`test_classify_frame_healthy_when_filled()` 里造的帧起点是
2026-08-20，而体检的 `TARGET_START` 是 2019-01-02 → 首行距窗口起点七年有余
→ 判成「历史被砍头」。于是「健康帧应该判健康」这条断言红了，
但红的理由和我要测的尾部空值毫无关系。

**修法**：给 `classify_frame` 传 `listing_date`，把首行解释成「本来就晚才有」，
头尾两项归零，此时不健康的**唯一**理由只可能是尾部空值。

**教训**：造 fixture 之前先问「它会不会撞上别的判据」。
一个测试红在错误的理由上，比测试不红更费时间——
它会把我推向错误的修改。

## 41. 用 1 字节假 parquet，被单票隔离吃掉，压根到不了被测代码

**经过**：`test_update_all_releases_lock_even_when_pipeline_explodes()`
里造了一个 `write_bytes(b"x")` 的假文件，期望它进到 `sync_daily` 抛
`KeyboardInterrupt`。结果报的是 `ArrowInvalid`（读不了），
被 `except Exception` 隔离成 `unreadable` 后 `continue`，
`sync_daily` 从来没被调用。

**教训**：`KeyboardInterrupt` 继承自 `BaseException` 不是 `Exception`，
所以它确实能穿透隔离层——前提是**代码真的走到了那一行**。
断言「某段代码被执行」时，要先确认造出来的数据能走通到那里。
测试绿得毫无意义（它绿在一个我根本没测的分支上）。

## 43. 硬编码的期望值算错了，而它「看起来被杀」

**经过**：给 `tail_nan_columns` 的窗口写变异体（`tail(5)` → `tail(20)`）时，
我补了一条测试：缺口放在 rows 8:13，`tail(5)` 够不到、`tail(20)` 够得到。
反证断言我写成：

```python
assert tail_nan_columns(df, Thresholds(halt_run=20)).get("turn") == 5   # 错
```

30 行的帧上 `tail(20)` 覆盖 rows **10:29**，而缺口在 rows 8:12，
重叠只有 **3 行**，不是 5。

**它没有立刻暴露**，因为跑变异测试时显示「✓ 被杀（1 failed, 12 passed）」——
变异体把窗口放大到 `halt(5)*4 = tail(20)`，在 `halt_run=20` 的调用下变成
`tail(80)`（整帧），缺口 5 行全在内，于是第二句成立、第一句被打破 → 判定「被杀」。

**未变异时这条断言其实是红的**，直到跑全量回归才暴露。

**这是最危险的一类错误**：断言**因为巧合而通过**，然后制造出它本该验证的那份信心。
变异测试的「被杀」只证明「测试红过」，不证明「红在正确的理由上」。

**修法**：期望值从帧本身算，不硬编码——

```python
expected = int(df.tail(20)["turn"].isna().sum())
assert expected > 0                                  # 反证不许空转
assert tail_nan_columns(df, Thresholds(halt_run=20)).get("turn") == expected
```

**教训**：只要期望值涉及窗口重叠、行数区间这类**需要算的东西**，
就让它从输入里算出来。硬编码的「5」看起来像规格说明，实际是个没验算的算式。

## 44. 用脚本做字符串替换，打中了两个同形字面量里的错误那个

**经过**：给 `backtest.py` 加 `_unknown_st` 计数，我用一段 Python 做
`str.replace()`，模式串是 `"_unfillable": {}}`。

结果它打中的是**空 `daily_map` 的早返回分支**那个字典，
主字典（真正的 `build_cross_sections`）没被改到，
于是运行时直接 `KeyError: '_unknown_st'`，21 个测试红。

**教训**：`replace()` 默认替换**全部**匹配，而「两个长得一样的字面量」
正是最容易看错的地方——我看到的那段和真正生效的那段只差一个缩进。
凡是替换必须唯一的地方，用 `edit` 并带足上下文，不要用脚本批量替。

（这条和第 42 条是同一族：**在文件上做批量文本操作，然后假设它落在了对的地方**。
两次都是「看起来成功了」。）

## 46. 变异体改错了地方：真正的清零在另一行

给熔断加变异体时，我把

```python
degrade_streak = (degrade_streak + 1 if result.status == "degraded" else 0)
```

改成 `degrade_streak += 1`，预期杀掉「连续变累计」的变异体。

**它没被杀掉，而且我一开始怀疑是僵尸变异体。** 真正的清零在 `else`
分支里，是**独立的一行** `degrade_streak = 0`。所以两个版本在
「降级/成功交替」下行为完全一样。

差异只在一支上：**未填上、但状态不是 degraded**（比如 `quarantined`）。
原始版本把它清零，变异版本会累加。

**教训**：变异体存活先分清「测试弱 / 变异体无效」，但还有第三种：
**变异体确实有效，只是你改的那一行不是承重的那一行**。
判据是「差异落在哪个输入分支上」，不是「源码文本变没变」。

补的测试把语义钉死了：`quarantined` 是数据不合格、源还活着，
**一次批量数据质量事件不该伪装成「源站挂了」并误熔断**。

## 47. 测试 helper 的参数顺序写错，还留了一个写死的路径

`_seed(tmp_path, n=12)` 调用 `_seed(n=12)`——把 `tmp_path` 传给了 `n`。
更糟的是 helper 里写着 `root = Path("_root") / ...`：
**测试数据写到了一个真实的固定目录**。

`TypeError: got multiple values for argument 'n'` 把它炸出来了。
如果签名碰巧对上（比如两个参数同类型），它就会安静地把文件写进
项目目录里——那才是真正麻烦的情形。

**教训**：测试 helper 里出现任何**写死的绝对/固定路径**，都是危险信号。
fixture 应该只往 `tmp_path` 里写，一处都不例外。

## 48. 拿到的是类不是实例

测试里 `pipeline = _patch(...)` 拿到的是我定义的 `FakePipeline` **类**，
我却去读 `pipeline.calls`（实例属性）→ `AttributeError`。

改法不是加 `__init__` 把列表挂上去，而是把调用记录提到闭包里
（`calls: list = []`），由 `_patch` 返回列表。
**共享的可变容器比在对象上挂状态更容易读，也更容易在多个测试间核对。**

## 49. 把接口返回的整个 JSON 打到终端上

查判决板 API 时我写了个「打印前 14 个键」的脚本，结果 API 返回的是
一个巨大的列表，于是**整份赛马数据刷满了输出**。

一条命令能吐出几万 token 的日志，比报错更贵——它把真正要看的东西淹了。

**教训**：调试输出先加长度上限。`[:300]`、`head -c`、
或者只取需要的字段。看不全的日志比没有日志更容易误导人，
因为它会让人以为「后面也没有别的了」。

**37 和 38 是同一件事的两面：我倾向于写出「聪明但我验不了」的代码。**

- 37：一行式 numpy，我自己推了两遍都推错，还是靠打印原始数据才发现；

而是因为它错的时候我看得出哪里错。

「测试绿」和「测试在测我想测的东西」之间隔着四道工序
（fixture 能走到被测行 / 断言的红在正确的理由上 / 变异体能杀死 /
测试挂进了目标清单），少一道就会出现「绿着的废话」。

**这一轮 7 起事故里，5 起是我自己的测试或 fixture 写错，
只有 1 起（36）是判断错误、1 起（38）是实现违背了自己的原则。**
生产代码的 bug 反而是最容易被发现的一类——
因为它有输入输出对得上，而测试里的 bug 要靠变异测试才照得出来。
