## 1. 现象（全库实测，逐文件只读所需列）

| 量 | 值 |
|---|---|
| 空值行数 | **53** / 8,721,078（空值率 0.000608%） |
| 涉及文件 | **53** / 5,458（0.971%） |
| 每只文件的空值根数 | 全部 `n_nan == 1` |
| 空值距文件末尾的偏移 | **只有 0 这一个取值**（53/53） |
| 空值所在日期 | **53/53 都是 2026-10-14**（正常交易日） |
| 空值列集合 | **53/53 完全一致**：`amount / tradestatus / isST / turn / pctChg` |

那 5 列正好是 `aplus/coverage.py:67::REQUIRED_EXTRA_COLUMNS`。
基线列 `date/code/open/high/low/close/volume` **一根都没缺**。

> ⇒ **唯一真缺口就是这 53 行 × 5 列**，全部压在 2026-10-14 那一根上。

## 2. ★ 最严重的后果不是 `amount`，是 `isST`

`isST` 为空 ⇒ **ST 过滤对这 53 只当天完全失明**。
一个「名字带 ST 的票」当天会被当成正常票进入候选池。

`amount` 空只影响成交额口径；`isST` 空影响**选股是否合规**。
⇒ **修的优先级由「哪一列影响决策」决定，不由「哪一列先被发现」决定。**

52/53 是 `688xxx`（科创板），1 条 `689009.SH`；科创板 621 只里 53 只中招（**8.5%**）。

## 3. 根因（直接证据，不是推断）

- 53 个坏文件 mtime 全部落在 **2026-10-14 19:51–19:53**（其余 5,405 个文件在 18:00–19:50）
- `data/logs/2026-10-14.jsonl` 里有 **55 条 `degraded_source_write`**，
  其中 **53 条的 code 与这 53 只完全相等**（另 2 条是整列缺失的 `000043.SZ` / `300114.SZ`）

```json
{"ts":"2026-10-14 19:53","event":"degraded_source_write",
 "code":"688737.SH","source":"tencent","primary":"baostock",
 "columns":7,"rows":2,
 "reason":"baostock: RuntimeError('baostock query failed: 10002007 网络接收...")}
```

⇒ **主源 baostock 网络挂 → 降级到腾讯（只有 7 列 OHLCV）→ `amount` 等 5 列不存在 → 写空。**
`rows: 2` 说明同时写了 10-13 与 10-14：
10-13 那天旧帧里有完整行，被 `store._merge_preserving_fidelity` 逐格填上；
**10-14 是新日期、旧帧里没有对应行可填 ⇒ 那 5 列空着**
（`store.py` docstring 自己写明了这个后果：「窄帧带来的新日期照常入库，缺列如实缺失，不编值」）。

**降级行为本身是对的**（宁可缺列也不编值）；缺陷在于
**降级写入的产物进了主库，而没有任何东西把它挡在判决之外**。

## 4. 为什么「不是停牌」（这一条必须钉死，否则会有人拿停牌解释掉它）

| 判据 | 53 只的末根 |
|---|---|
| `volume > 0` | **53 / 53**（当天真金白银成交了） |
| `high == low`（无日内振幅） | **0 / 53** |
| `close` 与前一日相同 | 仅 2 / 53 |

且全库 `volume == 0` 的 29,028 行里，`amount` 为 NaN 的有 **0 行**、为 `0` 的有 **29,028 行**。

⇒ **停牌日语义是 `0`，不是 NaN。**
⇒ `amount = NaN` 在这个库里**只有一个含义：缺列**。

## 5. ★ 处理顺序（**写死，防止「先改判据让它变绿」**）

| 步 | 动作 | 为什么必须在这个顺序 |
|---|---|---|
| **1** | **先修数据**：重拉这 53 只 2026-10-14 的尾根 | 洞的根因在数据侧。守卫放宽**不应该**先于数据补齐 |
| **2** | 数据补齐后，`test_the_real_store_amount_has_no_null_values` **应当自己转绿** | 若不绿 ⇒ 还有别的洞，必须继续查，不能进第 3 步 |
| **3** | 仍红的部分才进白名单 | 白名单是**登记已知例外**，不是**把有洞合法化** |

🚨 **直接放宽成 `nan_rows <= 53` 或 `<= 1%` 是错的**：
那是让「有洞」变成合法状态，而且**洞长大时不会喊**。

白名单若最终需要，形状对齐同文件里已有的 `KNOWN_BAD`
（`test_the_real_store_has_no_amount_contradiction`）：
新增即红 + 数据补上后**要求自己删条目**（`KNOWN_BAD - got` 必须为空）。

## 6. 诊断层该补的一件事（比放宽守卫更重要）

`scripts/measure_amount_availability.py::measure` 现在只报一个 `nan_rows` 总数，
**把「停牌」与「缺列」两种语义不同的空值混进了同一个数字**。

⇒ 建议加一个并列计数 **`nan_rows_with_volume_gt0`**（读 `volume` 列时顺手就有）：
`volume > 0` 当天真的成交了，此时的空值**一定是缺口**。

> 数据层这个区分早就存在 —— `aplus/backtest.py:485-486` 的 `_bars_tradable`
> 用 `np.isfinite(amt)` 把「缺失」与「为 0」分开。**只有诊断层没跟上。**
