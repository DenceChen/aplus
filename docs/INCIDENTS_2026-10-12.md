## 0. 先更正一条错误结论（比新缺陷更重要）

### ❌ 昨日结论：「90 只股票的文件被截断，根因未定位」

`INCIDENTS_2026-10-11.md` 的「仍未解决的」里写着：

> 有一处**能截断文件的代码路径尚未定位**……`LocalStore._upsert` 是
> `concat + drop_duplicates(keep='last')`，**结构上不可能截断**。
> 怀疑有代码绕过 store 直接 `to_parquet` 覆盖。

**这条是误判。数据完全正常，代码也没有问题。**

我当时的判定是启发式的：行数 < 中位数的一半（1882），即 591 只；

（起点 2019-01-02 = 数据集起点，止于 2019–2022 年）。

**用 baostock 上市/退市登记簿全量复核的结论**：

    行数 < 1882 的：2122 只
      ✅ 已退市（末行 <= 退市日）        236
      ✅ 次新股（首行 >= 上市日且未退市） 1886
      ❓ 无法解释                        0

反向也查了：末行 == 全库最新日（2026-10-09）的 5224 只里，
登记簿显示已退市的有 **0** 只。

逐只对上号的证据：

| 代码 | 登记簿退市日 | 文件末行 |
|---|---|---|
| `000418.SZ` | 2019-06-21 | 2019-06-21 |
| `000043.SZ` | 2019-12-16 | 2019-12-13（退市前最后一个交易日） |
| `000018.SZ` | 2020-01-07 | 2020-01-07 |

**教训**：
1. **「结构上不可能」不等于「我查得不够」**。`_upsert` 不会截断是对的，
   但我据此推断「必有代码绕过 store 覆盖」，跳过了最简单的一步——
   **先问这些股票是不是本来就该这么短**。停牌与退市是最平凡的解释。
2. 排查数据异常时，**上市/退市登记簿是权威判据，不是启发式**。
   本项目 `aplus/coverage.py` 早就写好了这条判据并注明「单看 parquet
   无法区分」，我却用行数阈值自己重造了一遍更差的版本。
3. 文件 mtime 是有用的旁证但不是证据：截断股的 mtime 散布在
   10-09 23 / 10-10 08 / 10-10 21 / 10-11 15 等多个时段，
   与正常股无异——**说明不是某一次坏写入**，这个反证当时就能推翻我的假设。

## 23. 体检只查「列在不在」，不查「列有没有值」

### 现象

2026-10-09 那批日线 K 线入库后，**末根的 5 个 baostock 专有列全是空的**。
全库实测：

    有 turn 列 5458 只｜末根缺失 3342 只（61.2%）｜整列不存在 2 只

缺口深度的分布说明这不是「某些票天生缺」：

    缺 1 根 → 3182 只      缺 2 根 → 6 只     缺 3~5 根 → 55 只

**3182 只恰好只缺最后 1 根**——这是「某次写入把某一根削薄了」的形状，
不是「这个因子历史上就没数据」的形状。

### 为什么体检没报出来

`aplus/coverage.py` 的 `coverage_gaps()` 只算 `missing_columns(df)`
——**列名在不在**。列在、但尾部整段为空的文件，体检一律判 `is_healthy=True`。

实测确证（真实文件）：

    601607.SH  tail_nan_columns = {'amount':1,'tradestatus':1,'isST':1,'turn':1,'pctChg':1}
               健康=False  原因=['tail_nan_cols']
    000665.SZ  tail_nan_columns = {}  健康=True

**这个盲区让缺口静默存在了三周。** 没有体检告警、没有测试、没有日志——
因为根本没有一个地方去看「这列的值是不是还在」。

### 修法

新增纯函数 `coverage.tail_nan_columns(df, th)`：
扫尾部 `halt_run` 根窗口，统计「**当天有成交**、但某列却是空」的根数。

关键约束是**不能把停牌误报成缺口**：停牌日 `volume=0`，`turn`/`amount`/
`pctChg` 为空是正常的（当天没成交，本就没有换手率可言）。所以
「有成交」是前置条件，判据只用 `volume > 0` 一条。

只查 `REQUIRED_EXTRA_COLUMNS`（`amount`/`tradestatus`/`isST`/`turn`/`pctChg`），
基线列不管——它们整列缺失归 `missing_columns` 管，重复报只会制造噪音。

新增体检原因 `tail_nan_cols`，插在 `missing_columns` 之后、
`head_truncated` 之前的优先级位置。

## 24. `isST` 空值被当成「非 ST」——ST 过滤对 61% 的股票失明

23 号那个洞的直接伤害，比「少一个因子」严重得多。

### 链条

`aplus/panel.py:536`：

```python
"isST": np.where(np.isnan(vals[keep, len(FACTOR_COLUMNS) + 1]), 0, ...)
```

NaN 的 `isST` 被折成 `0`，而 `0` 的语义是「**不是** ST 股」。
于是**缺数据 = 声称自己正常**——过滤器在最需要它的时候最不设防。

### 实测影响

2026-10-11 出的那 20 只推荐（`data/reports/holdings.json`），
末根 `isST` 为空的有 **6 只（30%）**：

    涨篮子 688137.SH 601579.SH
    跌篮子 600076.SH 002536.SZ 688433.SH 603890.SH 600749.SH

**跌篮子 10 只里有 5 只是 ST 筛查盲区。**

### 实测没有造成实际损失——但这是运气，不是防线

逐只查这 7 只的 `isST` 历史：最近一次有值的 `isST` **全是 0**
（`600749.SH` 历史上戴过 64 天帽，但最后一次有效值是 0）。
所以**今天这份名单里没有真的 ST 股**。

说清楚这个区别很重要：**ST 股没有混进名单，是因为这 6 只恰好都不是 ST，
不是因为防线起了作用。** 一只在 2026-10-09 当天被实施其他风险警示的股票，
会毫无阻碍地出现在推荐里，而且不会有任何告警。

同族的还有 `tradestatus` 空 → 停牌判定失灵；`pctChg`/`amount` 空 →
依赖这两个因子的评分失真。

### 修法（本轮已完成「让问题看得见」这一半）

23 号的 `tail_nan_columns` 把这类文件从「健康」翻成「不健康」，
并让 `backfill_gaps` / `repair_tail_cols` 知道该去补它们。

**根子上那一半也改了**：原先 `isST` 在两处被折成 0——
`panel.py:536`（快路径）和 `snapshot.py:90`（慢路径）。
两处现在都**如实传递 NaN**，并且 `filter_universe` 新增
`unknown_st` 计数器按日累加「ST 状态未知」的股票，
`run_daily` 出单时直接打印数量与样本。

    [predict] ⚠️ ST 状态未知 6 只（末根 isST 缺失，已按「不是 ST」放行）
             ——数据补齐后此项应归零

### 为什么先做「可见」而不是「fail-closed」

`filter_universe` 的 docstring 里记着一条实测：**要求 `isST == 0` 才保留，
会砍掉 88% 的正常股票**（`isST` 曾大面积缺失）。在数据还有洞的当下改成
fail-closed，等于让平台直接不可用。

正确的顺序是：**先让洞看得见 → 补洞 → 数据干净后 fail-closed 才有意义**。
顺序反了就是拿可用性换安全感，而洞还在原地。

补完 3101 只之后未知项归零，那时再回头评估要不要 fail-closed——那时是
一个能用数据回答的问题，不是现在的拍脑袋。

## 25. `daily_update.py` 没有任何写库互斥

### 现象

四个脚本都写 `data/master/daily/*.parquet`：
`bootstrap_history` / `backfill_gaps` / `repair_tail_cols` / `daily_update`。

补锁之前的状态：

- `backfill_gaps.py`：手搓 `if lock.exists(): 退出`
- `repair_tail_cols.py`（本日新建）：照抄了同一段
- **`daily_update.py`：一点锁都没有**

`daily_update` 由 launchd 每天 18:30 触发。只要它和任何一次回填撞上，
两个进程同时对同一个文件做 `concat + to_parquet`，后写覆盖先写——
**丢的列和行不会有任何人知道**。

### 第二层问题：check-then-act

即便有 `if lock.exists()` 也是竞态：两个进程可以同时看到「不存在」
然后都以为自己拿到了锁。必须用 `O_CREAT|O_EXCL` 让内核保证原子。

### 修法

新增 `aplus/write_lock.py`，三处统一调用：

- `O_CREAT|O_EXCL` 原子获取
- 锁文件里写 pid，**但不自动判活抢占**——把一个「其实还活着、只是慢」
  的进程误判成死的，比等它跑完危险得多；真要抢显式传 `force=True`
- 释放前核对 pid 归属，避免删掉别人的锁
- 异常退出（`__exit__`）也放锁——一次崩溃锁死全市场，
  第二天 18:30 就会静默跳过更新

## 26. 降级源写入是 23 号的成因（根因仍未消除）

`aplus/pipeline.py` 的单源存活分支：

```python
self.store.upsert_daily(code, primary)   # 保列由 store 保证
```

`LocalStore._merge_preserving_fidelity` 做的是「并集列 + 择多 + 少者填空」。
对**新日期**而言，旧帧里根本没有那一行，**没有任何东西可填**——
于是末根就只剩备源给的 OHLCV，五列全空。

所以 23 号的洞是这么形成的：

    腾讯备源（仅 OHLCV，~640 日）写入了 2026-10-09 这一根
      → 旧帧无此日期可填
        → amount/tradestatus/isST/turn/pctChg 全空
          → 体检只查列名，判健康（缺陷 23）
            → isST 空被折成 0，ST 过滤失明（缺陷 24）

**根因（降级写入本身）仍未消除**，本次只是补数据和补体检。
任何人再跑一次会降级的同步，都可能重新制造同样的洞——
这正是 `backfill_gaps.py` 默认 `--allow-degraded` 关闭的原因。

## 27. 主源会话中途死亡，961 只白跑 16 分钟

首轮全量修复（3101 只）的结果：

    修复完成：填上 2140｜未填 961｜异常 0

961 只**全部**是 `status=degraded`，且起点精确落在**第 2141 只**。
之后每次调用都由腾讯备源顶上——备源只有 OHLCV，
**填不上要补的五列**，于是每只都白跑一次网络往返还必然失败。

手工复现确认源站其实有数据：

    baostock 直连 603605.SH 2026-10-09 → turn=1.3295, isST=0, amount=294040074.88

隔几分钟重跑同一只，立刻成功。**不是数据缺失，是会话中途断了。**

### 为什么「异常 0」不能当成功信号

`degraded` 不是异常，`sync_daily` 也不抛错——它安静地返回了一个
「成功但没用」的结果。异常计数是 0，未填数是 961。
**只看异常数，这个失败会完全隐形。**

救回来的是 23 号那条纪律：**写完重读文件复验**。
961 条 `status=degraded` 一条不漏地被记下来，
最后还打印了前 30 只的具体缺列。

### 修法：连续降级熔断

```
连续 N 次 degraded → 判定主源会话已死 → 停，报出还剩多少只没处理
```

判据是**连续**而不是**累计**——累计失败会被中间的成功稀释，
连续失败才说明会话整体死了（中间成功一次就清零）。

另外把 `degraded` 与 `quarantined` 区分开：后者是数据过了
sanity/cross-check 被拒，源还活着，**一次批量数据质量事件
不应该伪装成「源站挂了」而误熔断**。

熔断只省时间，不影响正确性——即使没有它，复验也保证了一条错数据都不会被留下。
但 16 分钟白等是实打实的浪费，而且会诱使人以后跳过复验。

## 检查清单（本轮新增 14 条，接 11 号的 38 条）

### 关于「数据看起来正常」

- [ ] 体检判健康的文件，抽 3 只**逐列看末根的值**，而不只看列名
- [ ] 缺数据的语义要分开：「不是 ST」和「不知道是不是 ST」不许共用一个 0
- [ ] 任何 `np.where(np.isnan(x), 默认值, x)` 都要问：这里的默认值是不是
      一个**断言**（例如「不是 ST」「没有停牌」）？是的话就该改成拒绝
- [ ] 一个因子的空值率若恰好集中在「最后一根」，是写入端问题不是因子问题
- [ ] 缺口深度分布比缺口总数更能定性：「只缺 1 根」和「缺 1871 根」是两种病

### 关于误判

- [ ] 报「数据被截断」之前，先查上市/退市登记簿（权威判据）
- [ ] 提出「必有代码绕过了存储层」这种结构性断言前，先排除平凡解释
- [ ] 多个文件共享同一个异常特征时，先假设它们**本来就这样**，再假设它们坏了
- [ ] mtime 分布分散 = 不是单次写入事件；这是推翻「坏写入」假设的现成反证

### 关于自己的测试与变异体

- [ ] 变异体存活时，逐个分清「测试弱」/「变异体无效（僵尸）」，不许含糊
- [ ] 僵尸变异体（源码文本变了、效果 no-op）要写明为什么 no-op，
      并换一个真正承重的变异点
- [ ] **新增测试后，必须把它挂进对应变异体的目标测试清单**——
      测试写了但钩子没接上，变异体照样显示「存活」，两处都是假信号
- [ ] 变异体清单里写的说明要与实际被测行为一致，改了实现要同步改说明
- [ ] 造测试数据时要检查它**能不能走到被测的那行**：
      1 字节假 parquet 会被单票隔离吃掉，测试绿得毫无意义
- [ ] 造帧的起点/终点要和体检窗口对得上，否则测的是另一个缺口
      （帧起点 2026 年却不传上市登记 → 判成历史截断，掩盖了要测的尾部）

### 关于锁与并发

- [ ] 每个写主库的脚本都必须持同一把锁，且锁的实现只有一处
- [ ] 新增写方时，把所有读方和所有写方都跑一遍（同一件事一份实现迟早漂移）
